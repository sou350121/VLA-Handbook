### 1.2 关键机制 (Key Mechanism)

SPARK 由四个核心组件构成：

1. **SAM3 感知层**：开放词汇检测/分割，从文本提示生成掩码 → 质心像素 + 中位深度 → 反投影到世界坐标系 3D 关键点
2. **Gemini 规划层**：单次调用（temperature=0.3），输出 YAML 格式的行为树（BT），基于 5 个基础原语 + 30+ 组合技能的类型化语法
3. **IK 控制器**：操作空间控制器（OSC），PyRobot IK 求解，每个原语内封装了闭环控制（力反馈下降、接触检测）
4. **分层恢复层**：三级递进恢复——(1) 原位扰动（wiggle），(2) 感知重锚定（ retract 10cm → 重跑 SAM3 → 重试），(3) 重新生成计划（实验中未启用）

⚡ **Eureka Moment**：位置变化改变的是物体像素位置而非任务结构——所以测试时计算应该花在感知（重新找到物体）而非重规划（重写计划）。这一洞察颠覆了 Code-as-Policy 范式的计算分配策略。

## 2. 数学核心 (Math Core)

📌 **Napkin Formula**（一行抓住本质）：
```
SPARK(task) = BT_plan  where  BT_plan = Gemini(I_annotated, K_3D, task_instr)
执行成功 = ∀ primitive_i ∈ BT_plan: PostCondition(primitive_i, SAM3_reground) ✓
```

**目标**：在零训练条件下，用最小化测试时 LLM 调用次数实现最大任务成功率。

**核心分解**：

```
成功率 P_success = P(BT正确) × P(感知锚定正确) × P(执行成功 | BT, 感知)
                ≈ 1.0    ×    P(SAM3检测到正确关键点)   ×   P(IK到达)
```

其中：
- `P(BT正确) ≈ 1.0`：5 个基础原语的类型化语法保证了计划结构正确性（Gemini 单次调用即足够）
- `P(SAM3检测到正确关键点)` 是瓶颈——自适应感知自一致性将其从基线提升到可用水平
- `P(IK到达)` 由 IK 求解器和 OSC 控制器保证，失败可追溯

**变量说明**：

| 符号 | 含义 | 来源 |
|------|------|------|
| `I_annotated` | 标注图像（SAM3 掩码 + 标签叠加） | 相机输入经 SAM3 处理 |
| `K_3D` | 3D 关键点集合（质心像素 + 中位深度反投影） | SAM3 掩码 → 深度 → 世界坐标 |
| `task_instr` | 任务语言指令 | e.g. "Put the bowl on the plate" |
| `BT_plan` | YAML 格式行为树 | Gemini 单次调用输出 |
| `PostCondition` | 每个原语的后条件检查 | 如 grasp 后力传感器读数 > 阈值 |
| `SAM3_reground` | 失败时重新运行 SAM3 检测 | 机械臂 retract 10cm 后重检测 |

> 符号与本文保持一致：SPARK 将感知作为唯一残差误差源，计划层由类型化语法保证正确性。

## 3. 带数字走一遍：玩具例子 (Worked Example)

假设任务：**"Put the bowl on the plate"**，场景中有 bowl、plate、ramikin 三个物体。

**Phase 1 — 自适应感知（仿真中）：**

```
Gemini 生成 3 个备选提示:
  prompt_1 = "white ceramic bowl"     → SAM3 检测: 置信度 0.62, 掩码面积 847 px²
  prompt_2 = "large round dish"       → SAM3 检测: 置信度 0.45, 掩码面积 1203 px² (碎片化)
  prompt_3 = "blue patterned bowl"    → SAM3 检测: 无匹配 (提示错误)

选择: prompt_1 (最高置信度 0.62, 单一检测)
bowl 关键点: pixel(320, 240), depth 0.45m → world (0.15, -0.05, 0.45)
```

**Phase 2 — 行为树规划：**

```
Gemini 单次调用输出 BT:
  Sequence(root)
  ├── MoveToKeypoint(target="bowl")           → 世界坐标 (0.15, -0.05, 0.45)
  ├── Grasp(target="bowl", force=2.0N)        → 力反馈下降至接触
  ├── MoveToKeypoint(target="plate")          → 世界坐标 (0.25, 0.10, 0.45)
  ├── Release(target="bowl")                  → 松开夹爪
  └── Wait(duration=0.5s)                     → 稳定等待
```

**Phase 3 — 执行与恢复（假设第一次 grasp 失败）：**

```
执行 MoveToKeypoint("bowl") → ✓ 到达
执行 Grasp("bowl") → ✗ 后条件检查失败（力传感器读数 < 阈值）

Tier 1 恢复: grasp_perturb（原位微动）→ ✗ 仍失败
Tier 2 恢复: retract 10cm → 重跑 SAM3 → 新检测:
  bowl 关键点: pixel(318, 242), depth 0.44m → world (0.15, -0.04, 0.44)
  （物体被轻微推动，但 label "bowl" 不变，BT 不变）
重试 Grasp("bowl") → ✓ 成功（力传感器读数 2.1N > 阈值）

继续执行剩余 BT: MoveToKeypoint("plate") → Release → Wait → ✓ 任务完成
```

**关键数字**：
- LLM 总调用：2 次（仿真）/ 1 次（实机）
- SAM3 运行次数：2 次（初始 + 恢复重检测）
- 无 LLM 调用的恢复尝试：2 次（Tier 1 + Tier 2）

## 4. 工程视角 (Engineering View)

| 工程维度 | SPARK 数值 | 含义 |
|----------|-----------|------|
| **LLM 调用/任务** | 1-2 次 | 仿真 2 次（提示生成 + BT），实机 1 次（仅 BT） |
| **延迟/任务** | ~5-15s（LLM 部分） | Gemini API 延迟主导；CaP-Agent0 每轮 ~9 次调用 × 多轮 |
| **SAM3 调用/任务** | 1-N 次 | 初始 1 次 + 每次 Tier 2 恢复 1 次 |
| **BT 大小** | ~5-15 节点 | 简单任务 5 节点，复杂任务（fold）~15 节点 |
| **跨具身迁移成本** | 0 | 同一 BT 语法 + 同一 SAM3 管道直接运行 |
| **内存占用** | 低 | 无需加载 VLA 模型权重；仅需 SAM3 + Gemini API |
| **量化误差** | 不适用 | 无神经网络策略推理 |
| **部署约束** | 需 RGB-D 相机 + IK 求解器 | 仿真用渲染深度，实机需 Azure Kinect/RealSense |

**工程含义**：

1. **控制频率**：SPARK 不在控制循环内运行 LLM——LLM 只在上层生成 BT，底层 IK 控制器以高频（~100Hz）执行。这与 VLA 的 ~10-20Hz 端到端推理形成对比。
2. **模块边界**：感知（SAM3）、规划（Gemini BT）、控制（IK/OSC）三层完全解耦，任一模块可独立替换（如换 YOLO 代替 SAM3、换 GPT-4 代替 Gemini）。
3. **部署约束**：零训练意味着无需收集演示数据或运行 RL——但需要精心设计的原语语法和可靠的深度估计。深色物体（如黑色衬衫）的 SAM3 检测失败是已知硬件瓶颈。

### 6.3 隐含假设 (Hidden Assumptions)

1. **任务结构不变假设**：SPARK 假设位置/描述变化不改变任务的高层结构。这在位置扰动下成立，但在 goal-task 扰动下（目标物体本身改变）不成立——论文已确认这一点。
2. **SAM3 足够假设**：系统性能瓶颈被定位为 SAM3 检测质量。论文假设开放词汇检测器能覆盖绝大多数常见物体，但对长尾物体（特殊工具、非常规形状）未做评估。
3. **单步 BT 足够假设**：SPARK 假设单一 BT 足以覆盖大多数操作任务。但对于需要中期视觉反馈的任务（如擦拭直到干净），这一假设不成立——论文承认需要「turn-level observation gate」。
4. **深度估计可靠假设**：3D 关键点依赖深度相机。仿真中使用渲染深度（完美），实机中使用结构光/ToF 深度（有噪声和盲区），两者差距未量化。
5. **Gemini 单次调用足够假设**：假设 temperature=0.3 的单次调用能生成正确的 BT。对于极其复杂的任务（多物体、多步骤、条件分支），可能需要多轮 refinement。

💡 **面试 Tip**：当被问到「SPARK 和 Code-as-Policy 的本质区别是什么？」时，回答：「不是计划表示的不同（BT vs 代码），而是测试时计算预算的分配策略不同——CaP 把计算花在重规划上，SPARK 把计算花在重感知上。位置变化改变的是物体像素位置而非任务结构，所以感知才是需要计算的层。」

## 8. 精讀建議 (Reading Guide)

- **值得精读原文的人**：
  1. 研究 VLA 鲁棒性和分布外泛化的研究者——SPARK 提供了 VLA 之外的零训练替代方案
  2. 需要快速部署多具身操作系统的工程师——同一 BT 语法跨三平台 68% 平均极具吸引力
  3. 探索测试时计算分配（test-time compute allocation）的研究者——SPARK 的感知优先策略是该方向的首个系统性验证

- **建议章节路径**：先读 §3 Method（四组件架构）→ 再看 §4.2 LIBERO-PRO Results（核心数据）→ 可跳 §2 Related Work（如需背景再回读）→ §5 Discussion（与 CaP-Agent0 的对比洞察最有价值）

- **不值得精读的理由**：如果你不做零训练/神经符号方法、已有可靠的 VLA 训练 pipeline 且不需要跨具身迁移、或者你的场景是固定布局的重复任务——读摘要即可。SPARK 的价值在于分布外鲁棒性和零训练部署，而非标准设置下的性能。
