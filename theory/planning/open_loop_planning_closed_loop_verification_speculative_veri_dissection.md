## 1. 核心架构/方法总览 (Overview / Architecture)

### 1.1 系统对比概览 (System Component Comparison)

| 组件 | 输入 | 输出 | 频率 | 延迟 | 角色 |
|------|------|------|------|------|------|
| Heavy VLA (Macro-Planner) | $I_0$, $L$, $s_0$ | $A_{\text{macro}}$ ($K=64$), $F_0$ | 低频 (规划边界) | 1.373s | 长视野规划 |
| Lightweight Verifier | $I_t$, $F_0$ | a'_t (参考动作) | 高频 (每控制步) | 0.081s | 在线验证 |
| Deviation Checker | a_t, a'_t | ℰ_t (偏差分数) | 每控制步 | 可忽略 | 重规划触发 |

**训练/推理差异**：
- 训练时：Heavy VLA 冻结，只训练 verifier
- 推理时：Verifer 冻结，Heavy VLA 仅在触发重规划时调用

### 1.2 关键机制 (Key Mechanism)

**为什么这样设计？**

1. **Speculative Decoding 的具身控制困境**：NLP 中 token 验证可并行，因为上下文已确定；机器人中动作验证依赖未来观测，而未来观测只能执行后获得
2. **延迟硬约束**：Heavy VLA 推理延迟 (1.373s) ≫ 控制间隔 (~0.1s)，无法每步调用
3. **折中方案**：规划时一次性生成 $K=64$ 步 + 规划上下文特征 $F_0$；执行时用轻量验证器持续监控

⚡ **Eureka Moment**：具身控制应该"规划昂贵但稀疏，验证便宜但连续"——把 speculative decoding 的"草稿 - 验证"范式翻转为"宏规划 - 在线验证"。

## 2. 数学核心 (Math Core)

📌 **Napkin Formula**（一行抓住本质）：

```
规划：(A_macro, F₀) = π_θ(I₀, L, s₀)
验证：ℰ_t = norm(||a'_t - a_t||₁), 若 ℰ_t > τ 则重规划
```

**目标**：在保持长视野规划能力的同时，恢复对环境变化的响应性。

**变量说明**：

| 符号 | 含义 | 来源 |
|------|------|------|
| $\pi_\theta$ | Heavy VLA 策略 | 预训练模型（如 OpenVLA-OFT） |
| A_macro | 宏动作 chunk，长度 K=64 | 公式 (4) |
| $F_0$ | 规划上下文特征 | VLA 倒数第二层 Transformer 特征 |
| a'_t | 验证器预测的参考动作 | 公式 (7) |
| a_t | 宏规划中的第 t 步动作 | A_macro 的元素 |
| ℰ_t | 归一化 L1 偏差 | 公式 (8) |
| $\tau$ | 安全阈值，默认 0.2 | 超参数 |

**直觉**：验证器不是要替代宏规划，而是判断"当前状态是否还符合规划时的假设"。偏差超过阈值说明假设失效，需要重规划。

## 3. 带数字走一遍：玩具例子 (Worked Example)

假设任务："拿起黑色碗放到盘子上"，$K=64$，$\tau=0.2$。

**$T_0$ 时刻（规划边界）**：
- Heavy VLA 接收 $I_0$（相机图像）、$L$（指令）、$s_0$（关节状态）
- 输出 $A_{\text{macro}} = [a_0, a_1, \dots, a_{63}]$ 和 $F_0$
- 执行 $a_0$（机械臂开始移动）

**$T_1$ 时刻（验证步骤 1）**：
- 新观测 $I_1$（碗可能滑动了）
- 验证器计算：E₁ = ViT(I₁), Z₁ = FC([E₁||F₀]), a'₁ = π_verify(Z₁)
- 假设 $a_1 = [0.02, -0.01, 0.05, \dots]$（规划的原动作）
- 假设 $a'_1 = [0.03, -0.02, 0.06, \dots]$（验证器参考动作）
- ℰ₁ = norm(||a'₁ - a₁||₁) = 0.12
- $0.12 \leq 0.2$ → 接受 $a_1$，继续执行

**$T_5$ 时刻（验证步骤 5，假设抓取失败）**：
- $I_5$ 显示碗未成功抓取
- $a_5 = [0, 0, -0.1, \dots]$（原计划继续下放）
- $a'_5 = [0.05, 0.03, 0.02, \dots]$（验证器建议重新接近）
- ℰ₅ = norm(||a'₅ - a₅||₁) = 0.35
- $0.35 > 0.2$ → **触发重规划**
- 丢弃 $[a_5, \dots, a_{63}]$，Heavy VLA 从 $I_5$ 重新规划

**效率计算**：
- 最佳情况（64 步全执行）：1 次 VLA 调用 / 64 步 = 0.016 次/步
- 最坏情况（每步重规划）：1 次 VLA 调用 / 步 = 1 次/步
- 实际（LIBERO 平均）：$6.7$ 次 VLA 调用 / episode $\approx 0.1$ 次/步

## 4. 工程视角 (Engineering View)

### 4.1 延迟/吞吐分析

| 指标 | BASE (K=8) | BASE (K=64) | SV-VLA |
|------|-----------|-------------|--------|
| 每 episode VLA 调用 | 14.5 次 | 2.3 次 | 6.7 次 |
| 每 episode Verifier 调用 | 0 | 0 | 13.3 次 |
| 每 episode 推理时间 | 15.9s | 5.7s | 8.8s |
| 成功率 (平均) | 96.0% | 79.5% | 90.9% |
| 相对加速比 | 1.00x | 3.15x | 2.17x |

**关键数字**：
- VLA 单次推理：1.373s
- Verifier 单次推理：0.081s（约 1/17）
- Verifier  overhead 可忽略，但能挽回 11.4% 成功率

### 4.2 部署约束

1. **显存需求**：推理约 16GB VRAM（LIBERO 仿真），ALOHA 真机约 18GB
2. **控制频率**：Verifier 需运行在控制频率（~10-100Hz），VLA 可低至 0.5-2Hz
3. **阈值调参**：$\tau=0.1$ 保守（重规划频繁），$\tau=0.4$ 激进（成功率高但可能漏检）

## 6. 能力与失败模式 (Capabilities & Failure Modes)

### 6.1 能做什么

| 场景 | 能力 | 原因 |
|------|------|------|
| 动态环境 | 检测执行偏差并触发重规划 | 验证器基于最新观测 |
| 长视野任务 | 保持 64 步规划能力 | Heavy VLA 提供长视野 |
| 计算受限部署 | 2.17x 加速下保持 90%+ 成功率 | Verifier 轻量 |
| 抓取失败恢复 | 早期检测并重试 | Figure 3 定性结果 |

### 6.2 不能做什么

| 限制 | 原因 |
|------|------|
| 无法处理规划特征 $F_0$ 本身错误的情况 | Verifier 依赖 $F_0$ 作为参考 |
| 阈值 $\tau$ 需要任务级调参 | 论文使用固定 $\tau=0.2$ |
| Verifier 需要额外训练数据 | 需从演示数据中学习参考策略 |
| 不适用于超高速控制（>100Hz） | Verifier 延迟 81ms 仍是瓶颈 |

### 6.3 隐含假设 (Hidden Assumptions)

1. **环境变化是渐进的**：假设验证器能在偏差累积到不可挽回前检测到
2. **规划特征 $F_0$ 包含足够信息**：假设倒数第二层特征能编码"规划意图"
3. **L1 距离是合适的偏差度量**：对于旋转/姿态动作，L1 可能不够敏感
4. **演示数据覆盖足够状态空间**：Verifier 训练依赖演示数据中的状态 - 动作对
