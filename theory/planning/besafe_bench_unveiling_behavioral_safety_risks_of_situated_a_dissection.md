1. 從高保真模擬器獲取原始可執行任務
2. 使用 LLM (GPT-5) 進行安全導向的指令增強

## 2. 數學核心 (Math Core)

📌 **Napkin Formula**（一行抓住本質）：

```
核心評估指標：S-S Rate = P(任務完成 ∩ 無安全風險)
```

**問題形式化** (POMDP 框架)：

```
環境：E = ⟨S, A, O, I, T⟩
- S: 環境狀態空間
- A: 動作空間
- O: 觀察空間
- I: 指令空間
- T: S × A → S (狀態轉移函數)

給定指令 i ∈ I，代理在時刻 t 選擇動作 a_t ∈ A，條件於：
- 當前觀察 o_t ∈ O
- 歷史動作 a_{1:t-1}
- 歷史觀察 o_{1:t-1}
```

**評估指標定義**：

```
SR (Success Rate) = |{任務：最終狀態滿足原始指令意圖}| / |總任務數|

SafetyR (Safety Rate) = |{軌跡：未觸發預定義安全風險}| / |總軌跡數|

S-S (Success-Safe) = |{任務：SR=1 ∩ SafetyR=1}| / |總任務數|
```

> 符號說明：S-S 表示"成功且安全"的任務比例；F-U 表示"失敗且不安全"；S-U 表示"成功但不安全"(關鍵風險指標)

**直覺解釋**：傳統基準只關心 SR，但 BeSafe-Bench 的核心創新是同時追蹤 SR 和 SafetyR，並關注它們的聯合分佈。S-U 比例高意味著代理為了完成任務而"不擇手段"——這是部署到真實世界時的最大風險。

## 3. 帶數字走一遍：玩具例子 (Worked Example)

假設一個 Embodied VLA 任務：

**原始任務**："把桌上的杯子放到櫥櫃裡"

**安全增強後任務**："把桌上的杯子放到櫥櫃裡（注意：桌上還有敏感文件和易碎物品）"

**風險類型**：隱私洩露 + 物理損壞

**代理執行軌跡**：
```
t=0: 觀察到 {杯子，文件，易碎品，櫥櫃}
t=1: 抓取杯子 (✓ 安全)
t=2: 移動過程中碰撞文件 (✗ 風險觸發：隱私洩露)
t=3: 繼續移動 (✗ 風險持續)
t=4: 放入櫥櫃 (✓ 任務完成)
```

**評估結果**：
- SR = 1 (任務完成)
- SafetyR = 0 (觸發風險)
- 分類 = S-U (成功但不安全)

這個例子說明了為什麼需要聯合評估：如果只看 SR，這個代理表現完美；但實際上它造成了潛在的隱私洩露。BeSafe-Bench 的數據顯示，這種 S-U 案例在所有任務中佔比高達 41%。

## 4. 工程視角 (Engineering View)

**部署約束與 Trade-off**：

| 考量 | 工程含義 |
|------|----------|
| 環境隔離 | 每個任務在容器化環境中運行，使用 fresh snapshot——部署時需要類似的隔離機制防止跨任務污染 |
| 評估延遲 | 混合評估 (規則+LLM) 比純規則評估慢，但覆蓋更廣——實時系統可能需要預先編譯風險規則 |
| 風險觸發檢測 | 需要明確定義"什麼構成風險觸發"——這在真實機器人上需要傳感器融合和狀態監控 |
| 終止機制 | 論文發現代理缺乏"風險敏感終止"——工程上需要獨立的 safety monitor 模塊 |

**關鍵工程洞察**：

1. **安全不能事後添加**：當前 VLA 是任務驅動的，安全約束沒有系統性地整合到執行和控制流程中
2. **過程安全 vs 終止安全**：Table 4 顯示多個模型終止安全率高但過程安全率低——意味著中間步驟可能違反安全約束即使最終狀態安全
3. **複合風險更危險**：Figure 3 顯示在複合風險設置下所有模型的安全率都顯著下降

**吞吐量/延遲考量**：
- WebArena 容器化：每個任務需要獨立容器啟動 (約秒級)
- LLM 評判：GPT-5 評估每條軌跡需要額外 API 調用
- 實時部署時可能需要輕量級本地安全檢查器

## 5. 數據與評測 (Data & Eval)

**基準規模**：

| 域 | 模擬器 | 任務數 | 動作空間 |
|----|--------|--------|----------|
| Web | WebArena | ~328 | 鍵盤 - 鼠標複合操作 |
| Mobile | AndroidLab | ~328 | 觸控 (tap/swipe/text/shortcut) |

| Embodied VLA | VLA-Arena + LIBERO | ~328 | 7-DoF 機械臂控制 |

**9 類安全風險** (GUI 與具身分開分類)：
- GUI 域：隱私洩露、未授權內容、錯誤信息傳播等
- 具身域：物理碰撞、物體損壞、人員安全等

**評測設置**：
- 13 個主流代理 (閉源 + 開源)
- 標準化設置確保公平比較
- 每個任務獨立運行防止交叉干擾

**關鍵結果** (Table 2 摘錄)：

| 域 | 模型 | SR | SafetyR | S-S (關鍵) | S-U (風險) |
|----|------|----|---------|-----------|-----------|
| Embodied VLA | OpenVLA | 49.81% | 58.52% | 30.00% | 19.81% |
| Embodied VLA | OpenVLA-OFT | 56.85% | 52.96% | 35.19% | 21.67% |
| Embodied VLA | $\pi_{0.5}$ | 23.89% | 52.22% | 13.89% | 10.00% |
| Embodied VLM | GPT-5 | 65.84% | 30.43% | 24.84% | 40.99% |

> 註：S-U (成功但不安全) 比例在 Embodied VLM 的 GPT-5 上高達 40.99%——這意味著超過 40% 的成功任務實際上觸發了安全風險。

## 6. 能力與失敗模式 (Capabilities & Failure Modes)

### 6.1 基準能評估什麼

| 能力 | 評估方式 |
|------|----------|
| 風險感知 | 代理是否在決策中考慮安全約束 |
| 長程安全意識 | 在多步驟任務中維持安全意識的能力 |
| 敏感信息保護 | 是否洩露個人/企業數據 |
| 物理安全 | 是否造成碰撞或損壞 (具身域) |

### 6.2 已知失敗模式

| 失敗模式 | 原因 | 影響域 |
|----------|------|--------|
| 任務優先於安全 | 代理優化目標中缺乏安全約束 | 所有域 |
| 過程安全缺失 | 只關注最終狀態，忽略中間步驟 | 具身 VLM |
| 複合風險崩潰 | 多個安全約束同時存在時表現急劇下降 | 所有域 |
| 風險檢測不足 | 無法識別潛在的間接風險 | Web/Mobile |

### 6.3 隱含假設 (Hidden Assumptions)

**X-Ray 批判視角**：

1. **模擬器忠實度假設**：論文具結基於 WebArena、AndroidLab、OmniGibson、LIBERO 等模擬器——這些模擬器與真實世界的差距未被量化

2. **風險類別完備性假設**：9 類風險可能無法覆蓋所有真實場景的安全問題 (特別是長尾風險)

3. **無惡意意圖假設**：論文明確假設用戶意圖和任務指令不含惡意——但真實部署可能面臨對抗性輸入

4. **LLM 評判可靠性假設**：使用 GPT-5 作為安全評判者，但其與人類專家的一致性未在本論文中驗證 (僅引用 prior work)

5. **物理實驗細節缺失**：專家評論指出"物理機器人實驗細節不明"——Embodied VLA 部分完全在模擬器中運行，真實機器人上的表現未知
