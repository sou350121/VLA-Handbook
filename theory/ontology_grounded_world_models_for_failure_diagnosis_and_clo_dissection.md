### 1.2 关键机制 (Key Mechanism)

Onto-EV-WM 的核心设计哲学是**分层解耦**：

- **预测层（不变）**：EV-WM 的视觉编码、世界模型、事件预测器全部冻结，不做修改
- **诊断层（新增）**：将预测的输出或仿真器观测映射到类型化 ABox（事实记录），与任务要求的 ABox 对比，识别未满足的谓词
- **修正层（新增）**：为每个类型化失败分配修正路径标签，由外部提议器生成修正
- **验证层（新增）**：修正后，用原始任务谓词（而非标量分数）验证是否接受

这种设计的关键优势是**可插拔**——诊断和修正接口与底层世界模型解耦，可以替换不同的提议器（学习式、启发式、规划基）而不影响预测层。

⚡ **Eureka Moment**：世界模型的标量分数告诉你"这个候选不够好"，但本体诊断告诉你"这个候选因为 in_region(plate, stove_front) 未满足而失败，修正路径是 state-level qpos delta"——**从"打分"到"诊断"的范式转换，是这篇论文最核心的洞见。**

## 2. 数学核心 (Math Core)

📌 **Napkin Formula**（一行抓住本质）：
```
ΔF^{src} = {f ∈ Facts(A_g^*) | Sat_T(f, A^{src}) = 0}
D^{src} = {(f, c_f, m_f) | f ∈ ΔF^{src}}
Accept = I[Verifier(Apply_r(s, P_r(s, A_g^*, d^†))) = 1]
```

**目标**：当世界模型预测的未来状态不满足任务要求时，系统需要（1）诊断出哪个谓词未满足，（2）分配修正路径，（3）生成并应用修正，（4）验证修正结果。

**变量说明**：

| 符号 | 含义 |
|------|------|
| A_g^* | 从任务规范 g 编译出的"要求的 ABox"（目标事实集合） |
| Â^{pred} | 从世界模型预测输出 grounding 的 ABox |
| A^{sim} | 从仿真器状态 grounding 的 ABox |
| Sat_T(f, A^{src}) | 判定事实 f 是否在 ABox 中满足（考虑极性、阈值、来源证据） |
| ΔF^{src} | 未满足的谓词集合（诊断输出） |
| d_f = (f, c_f, m_f) | 类型化失败记录：谓词 + 失败类型 + 阈值余量 |
| Π_R | 确定性路由映射：失败记录 → 修正路径标签 |
| P_r | 提议生成器：可学习/启发式/规划基 |
| B | 最大重试预算 |

**直觉**：把世界模型的"标量评分"问题转化为"结构化诊断"问题。不是回答"这个候选好不好"，而是回答"这个候选哪里不好、怎么修、修完对不对"。

> 符号与本文保持一致：A 表示 ABox，φ 表示 grounding 操作，Π 表示确定性规则，P 表示提议生成器，I 表示指示函数。

## 3. 带数字走一遍：玩具例子 (Worked Example)

假设一个 LIBERO-Goal 任务：`put plate_on stove_front`。

**第 0 步 — 构建要求的 ABox**：
```
A_g^* = {in_region(plate, stove_front), gripper_open, no_collision}
```

**第 1 步 — 世界模型预测并 grounding**：
```
Â^{pred} = {near(plate, stove_front)=0.72, gripper_open=1.0, no_collision=1.0}
```

**第 2 步 — 诊断**：
```
Sat_T(in_region(plate, stove_front), Â^{pred}) = 0  // near ≠ in_region
ΔF = {in_region(plate, stove_front)}
D = {(in_region(plate, stove_front), type=spatial_relation, margin=0.28)}
```
注意：标量分数 0.72 告诉你"接近但不满足"，但不知道缺什么。诊断记录明确告诉你缺 `in_region`，余量 0.28。

**第 3 步 — 路由与修正**：
```
r = Π_R(d) = "state/qpos_delta"  // 路由到状态级 qpos 修正
q = P_r(s, A_g^*, d) = Δqpos 使得 plate 向 stove_front 移动
s' = Apply(s, q)  // 直接修改仿真器 qpos
```

**第 4 步 — 验证**：
```
Verifier(s') = env.check_success() = 1  // in_region 现在满足
Accept = 1  // 修正被接受
```

**如果失败**：b=0 失败 → b=1 重新 grounding → 可能选择不同路由 → 最多 B 次。

## 4. 工程视角 (Engineering View)

| 维度 | 分析 |
|------|------|
| **计算开销** | 诊断层是确定性规则（轻量），修正提议器可能是神经网络（需 GPU）。总体增加 ~5-15% 推理时间（取决于提议器复杂度） |
| **延迟** | 单次诊断+修正循环约增加 10-50ms（仿真环境）；真实机器人上受控制器频率限制 |
| **内存** | ABox 记录是结构化数据，内存占用极小（每个任务 ~KB 级） |
| **部署约束** | 需要为每个任务域手动定义 TBox（实体类型、谓词签名、约束）——这是主要工程瓶颈 |
| **模块化** | 高：预测层/诊断层/修正层/验证层完全解耦，可独立替换 |
| **可扩展性** | 新任务域需要手动编写 TBox + 路由映射，自动化程度低 |

**工程含义**：Onto-EV-WM 的架构设计适合"任务域有限但可靠性要求高"的场景（如固定家务机器人），不太适合需要频繁切换任务域的通用平台。TBox 的手动定义是主要瓶颈——如果能从任务描述自动推断 TBox，可扩展性将大幅提升。

## 6. 能力与失败模式 (Capabilities & Failure Modes)

### 能做什么
- **诊断失败原因**：不仅知道"失败了"，还知道"哪个谓词未满足、余量多少"
- **闭环修复**：修正→验证→重试，最多 B 次循环
- **可插拔修正器**：支持学习型、启发式、规划基三种提议器
- **来源感知**：区分预测 grounding 和仿真器 grounding，不同来源用不同 grounding 策略

### 不能做什么
- **不能自动定义 TBox**：每个任务域需要手动定义本体词汇表
- **不能跨域泛化**：TBox 是任务局部的，不声称通用机器人本体
- **不能保证修正可行性**：修正直接修改仿真器状态（LIBERO）或通过控制器执行，但修正本身不一定动态可执行
- **未评估真实机器人**：所有实验在仿真中，sim-to-real 迁移未验证

### 6.1 隐含假设 (Hidden Assumptions)

| 假设 | 说明 | 风险 |
|------|------|------|
| TBox 可手动定义 | 假设每个任务域的谓词集合是有限的、可枚举的 | 开放世界场景中谓词可能无法穷举 |
| 修正路径可预先映射 | 假设失败类型到修正路径的映射是确定性的 | 复杂场景可能需要在线路由选择 |
| 仿真器状态可修正 | LIBERO 实验中直接修改 qpos，这在实际机器人上不可行 | 真实系统需要通过控制器执行，修正可行性不确定 |
| 验证器可靠 | 假设 env.check_success() 是任务成功的充分条件 | 仿真中的成功检查可能过于简化 |
| 本体贡献可叠加 | 假设本体层的增益与底层世界模型独立 | 论文明确承认"ontology-only causal share 未单独测量" |
