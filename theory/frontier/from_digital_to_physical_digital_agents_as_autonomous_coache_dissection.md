### 1.2 关键机制 (Key Mechanism)

RoboCoach 的核心是一个三层反馈闭环：

1. **文本执行信号（Textual Execution Signals）**：检测实现失败——语法错误、运行时异常、依赖配置错误。通过 10 episode 的轻量 debug_test 在提交完整训练前捕获实现问题。
2. **量化训练信号（Quantitative Training Signals）**：检测优化失败——学习不稳定、奖励崩溃、停滞。智能体自主查询 W&B 等实验追踪工具的奖励曲线、损失轨迹和运行成功率。
3. **视频 Rollout 观察（Video Rollout Observations）**：检测行为失败——不稳定接触、错误抓取姿态、低效运动、目标附近轨迹偏差。VLM 将 rollout 视频转换为结构化行为诊断。

⚡ **Eureka Moment**：智能体不需要直接的感觉运动具身——它只需要一个能让物理后果"可读且可操作"的系统架构。三层反馈分别诊断实现失败、优化失败和行为失败，每一层解决其他层不可见的问题。

## 2. 数学核心 (Math Core)

📌 **Napkin Formula**（一行抓住本质）：

```
π* = arg max_π E[success(π)]  s.t.  π 由 LLM Agent 通过闭环搜索得到
     其中搜索空间由树状记忆组织，反馈信号 f = {f_text, f_train, f_video} 引导
```

**目标**：让数字智能体通过闭环反馈，将自然语言任务规范转换为能完成物理任务的成功策略。

**关键变量**：

| 符号 | 含义 |
|------|------|
| T = (D_prd, P_sys, C_env) | 任务三元组：语义规范 + 操作接口 + 开发环境 |
| D_prd | 结构化自然语言文档（目标、约束、领域先验，无演示/奖励梯度） |
| P_sys | 操作接口（Terminal + FileEditor + TaskTracker） |
| C_env | 开发环境（improving: 已有代码库 / from-scratch: 骨架模板） |
| f_text | 文本执行信号（语法/运行时错误） |
| f_train | 量化训练信号（奖励曲线/损失轨迹/成功率） |
| f_video | VLM 视频诊断（行为级失败描述） |
| $\text{success}(\pi)$ | 二元任务完成率（100 episodes 评估） |

> 符号与本文保持一致：T 定义智能体可知道和可做的边界；f 三层反馈构成物理接地信号；成功仅由物理任务完成率衡量。

## 3. 带数字走一遍：玩具例子 (Worked Example)

假设一个 diffusion policy 在 ManiSkill 的 PickCube 任务上：

**第 1 轮（One-shot 生成）**：
- LLM 生成训练代码 → 编译通过但训练发散（reward 从 0.5 降到 0.1）
- f_text: 无错误（代码能跑）
- f_train: 奖励崩溃，loss 震荡 → 诊断：学习率过高 + 缺少梯度裁剪
- f_video: 机械臂在接近物体时抖动 → 诊断：动作不平滑

**第 2 轮（基于反馈修改）**：
- Agent 添加梯度裁剪（clip_norm=1.0）、降低学习率（1e-3 → 3e-4）、添加动作平滑正则化
- 训练：reward 稳定上升到 0.65
- f_train: 学习正常但 plateau
- f_video: "机械臂能接近物体但抓取时机过早，物体被推开而非抓住"

**第 3 轮（行为级修正）**：
- Agent 增加模型容量（hidden_dim 256→512）、延长时间视野（horizon 16→32）、添加状态增强
- 训练：reward 上升到 0.82
- 最终成功率（100 eval episodes）：0.85
- 人类专家基线：0.72

这个例子展示了三层反馈的层级关系：先让代码跑起来（f_text），再让训练收敛（f_train），最后让行为正确（f_video）。

## 4. 工程视角 (Engineering View)

| 工程维度 | 说明 |
|----------|------|
| 每任务 API 调用 | 未明确量化（分支搜索意味着多次 LLM 调用，每轮至少 1 次） |
| 仿真开销 | 每轮需完整训练 + 100 episode eval；diffusion policy 训练可能需要数小时 GPU |
| 内存管理 | 树状记忆存储所有历史实验——随迭代深度增长，需剪枝策略 |
| 部署约束 | 需要 LLM API（GPT/Gemini 等）+ VLM API + 仿真环境；不适合边缘部署 |
| 并行性 | 不同分支可并行探索，但单分支内串行 |
| 量化/精度 | 论文提到 Agent 自动启用 mixed-precision 训练以支持更大模型 |
| 容错性 | 自动修复 checkpointing 失败、运行时错误、验证逻辑 bug |

**工程含义**：RoboCoach 不是超参搜索——它是"训练管线"的自动化。Agent 同时修改模型架构、数据处理、优化器、验证逻辑、基础设施，每个改动都通过下游物理任务完成率评估。这意味着它比 AutoML 更灵活，但也更昂贵。

## 6. 能力与失败模式 (Capabilities & Failure Modes)

### 能做什么

| 能力 | 场景 |
|------|------|
| 自动代码修复 | One-shot 生成无法运行的代码 → 通过执行反馈修复 |
| 奖励函数优化 | 手动奖励设计 → Agent 自动调整奖励项权重和形式 |
| 策略架构选择 | 在 MLP/ACT/Diffusion/VLA 之间选择并优化 |
| 训练稳定性 | 自动添加梯度裁剪、EMA、混合精度、学习率调度 |
| 行为级诊断 | VLM 观察 rollout 视频，发现标量指标看不到的行为问题 |
| 真实迁移 | 仿真优化的策略可迁移到真实机器人 |

### 不能做什么

| 局限 | 原因 |
|------|------|
| 接触密集型操作仍有困难 | 代码级修复空间有限，需要更细粒度的控制 |
| 计算成本高 | 分支搜索 + 完整训练循环 = 大量 API 调用和 GPU 时间 |
| 依赖结构化任务定义 | 假设任务规范明确、评估协议固定 |
| 不衡量样本效率 | 只评估最终成功率，不评估达到成功所需的交互次数 |
| 无安全性保证 | 二元成功指标不捕捉 near-miss 或安全关键失败 |
| 真实验证有限 | 仅 4 个真实机器人任务，形态/传感器/部署条件多样性不足 |

### 6.1 隐含假设 (Hidden Assumptions)

1. **任务规范是良定义的**：论文假设 D_prd 包含足够清晰的优化目标和约束。但在实际研究中，任务定义往往模糊且需要迭代澄清。
2. **仿真到真实的迁移是可行的**：4 个任务的迁移结果积极，但远不足以覆盖开放世界机器人的多样性。
3. **VLM 视频诊断是可靠的**：将行为诊断委托给 VLM 是一个关键假设——VLM 的幻觉或误判会直接误导 Agent 的修改方向。
4. **树状记忆的规模可控**：随着迭代深度增加，记忆树可能变得庞大。论文未讨论记忆管理的工程细节。
5. **计算预算不是瓶颈**：分支搜索的计算开销未量化。在实际部署中，每任务的 API + GPU 成本可能很高。
