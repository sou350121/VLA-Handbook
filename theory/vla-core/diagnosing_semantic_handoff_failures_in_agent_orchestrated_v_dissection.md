### 1.2 关键机制 (Key Mechanism)

系统分为两层：

**Agent 层**（上层）：
- 任务分解 → 技能调用序列  
- 维护 typed skill contract：`s_t = (name, args, prompt, B_s, K_s, ϕ_t)`
- 执行 plan-act-verify-replan 循环
- 触发恢复（re-navigation / retry / replan）
- 记录可回放 trace（日志、视频、证据）

**Embodiment 层**（下层）：
- BEHAVIOR-1K / OmniGibson 仿真环境
- $\pi_{0.5}$ VLA 推理（PaliGemma 视觉骨干 + flow-matching 动作头）  
- 三视图 RGB 输入（头部 + 双腕）+ 本体感知状态
- 低层动作执行

⚡ **Eureka Moment**：同一个 VLA 检查点在孤立评测中达到 77-100% 成功率，但在组合执行中几乎全部失败——瓶颈不在技能本身弱，而在技能边界的分布偏移。这意味着"训练更多数据"不会解决问题，因为新增数据只会强化已胜任的干净分布，而非覆盖链状态。

## 2. 数学核心 (Math Core)

📌 **Napkin Formula**（一行抓住本质）：

```
技能组合成功率 ≈ Π_t P(ϕ_t ∧ ρ(s_t, s_{t+1}) | s_t.start_from_chained_state)
```

**目标**：最大化长程任务中每个技能步骤的成功转移概率，其中转移不仅要求当前技能后条件 $\phi_t$ 满足，还要求下一技能就绪性谓词 $\rho(s_t, s_{t+1})$ 成立。  

**公式拆解**：

```
P(task_success) = Π_{t=1}^{T} P(ϕ_t ∧ ρ(s_t, s_{t+1}) | s_t 从 s_{t-1} 的终端状态启动)
```

**变量说明**：

| 符号 | 含义 |
|------|------|
| $\phi_t$   | 技能 s_t 的后条件（postcondition），如"目标在视野内" |
| $\rho(s_t, s_{t+1})$   | 下一技能就绪性谓词（future work），如"目标在机械臂可达范围内" |
| s_t.start_from_chained_state | 技能 $s_t$ 从 $s_{t-1}$ 的终端状态启动（而非干净 snapshot）   |
| T | 任务总技能数（BEHAVIOR-1K 中通常 5-10 个） |
| B_s | 技能步数预算（budget），VLA 缺乏可靠停止信号 |
| K_s | 验证间隔（verifier interval），当前 K=200 环境步 |
| $\rho$ 的实例化 | $R_{\text{name}(s_{t+1})}(\text{args}(s_{t+1}), o_t)$，$o_t$ 为当前多视图视觉证据   |

**直觉**：如果每个技能的交接成功率是 90%，10 步任务的总成功率只有 0.9^10 ≈ 35%。而论文中孤立成功率虽高（77-100%），但组合场景下交接成功率远低于此，导致累积崩溃。

> 符号与本文保持一致：$\phi$ 表示后条件，$\rho$ 表示就绪性谓词（未来工作），$s_t$ 表示第 $t$ 个技能调用。  

## 3. 带数字走一遍：玩具例子 (Worked Example)

假设一个 5 步任务：`[move_to(kitchen), open(microwave), pick_up(bag), place_in(bag, MW), close(MW)]`

**场景 A：孤立评测（干净 snapshot）**

每个技能从演示恢复的干净状态启动：

| 步骤 | 孤立成功率 | 链式成功率（论文观测） |
|------|-----------|---------------------|
| move_to | 77% (27/35) | ~40%（估计，从门后状态启动） |
| open_door | 100% (7/7) | ~50%（相机视角偏移） |
| pick_up | 97% (28/29) | ~30%（夹爪位姿偏移） |
| place_in | 85% (11/13) | ~20%（目标位置不确定） |
| close_door | TODO: 论文未单独报告 | ~40%（估计） |

累积成功率：
- 孤立场景：$0.77 \times 1.0 \times 0.97 \times 0.85 \times 0.80 \approx 51\%$  
- 组合场景：$0.40 \times 0.50 \times 0.30 \times 0.20 \times 0.40 \approx 0.2\%$  

这解释了为什么论文观测到"近零任务成功率"。

**场景 B：失败归因分布（130 次失败尝试）**

论文从一轮代表性执行中归因了 130 次失败：

| 失败类别 | 占比（估计） | 典型场景 |
|----------|-------------|---------|
| 控制执行 (control execution) | ~45% | VLA 从链状态出发无法收敛到目标，耗尽步数预算 |
| 目标锚定 (target grounding) | ~30% | 开门后目标移出视野，或对象实例模糊 |
| 下一技能就绪 (next-skill readiness) | ~25% | 导航完成但目标不在机械臂可达范围内 |

**关键洞察**：如果收紧导航验证器（要求"机械臂可达"而非仅"同区域可见"），额外发现 12 次就绪性失败和 25 次重新导航尝试，并成功恢复了 radio 任务。这说明验证器标准本身就是一个杠杆。

## 4. 工程视角 (Engineering View)

| 工程维度 | 当前实现 | 含义 / Trade-off |
|----------|---------|-----------------|
| 验证器调用频率 | K=200 环境步/次 | 频率太低→延迟检测失败；太高→VLM API 成本和延迟增加   |
| 验证器模型 | gemini-2.5-flash | 低成本但可能误判；20/21 人工审计一致率（过严格 0.05） |
| 技能步数预算 | 按技能类型预设 B_s | VLA 无可靠停止信号，预算过紧→提前终止；过松→浪费时间   |
| 全局 episode 预算 | $2\times$ 人类演示长度   | 允许有限重试，但限制了探索空间 |
| 恢复策略 | re-navigate → retry   | 简单但有效；缺少更丰富的恢复模式（如改变抓取角度） |
| 推理延迟 | 3 视图 RGB + 本体状态 → $\pi_{0.5}$ → 动作   | $\pi_{0.5}$ 的 flow-matching 推理速度 TODO: 论文未报告   |
| 内存占用 | PaliGemma 骨干 + flow-matching 动作头 | 三视图输入增加显存需求，但比多模型方案更紧凑 |

**工程含义**：这个架构的核心 trade-off 是"验证精度 vs 执行效率"。每次验证需要调用 VLM（gemini-2.5-flash），每 200 步一次。对于 10 步任务，每步平均 3-5 次验证尝试，总验证调用约 50-100 次。如果 VLM 每次调用 1-2 秒，仅验证就增加了 50-200 秒开销。

## 5. 数据与评测 (Data & Eval)

**训练数据**：
- 来源：BEHAVIOR-1K 遥操作演示（清洗为技能片段）
- 两阶段训练：
  1. 全技能中期训练（pooled all-skill mid-training）
  2. 技能组专项微调（skill-group specialization）
- 技能库覆盖 9 种技能类型：move_to, pick_up_from, place_on, place_on_next_to, place_in, press, turn_on_switch, open_door, close_door

**评测设置**：
- 基准：BEHAVIOR-1K public test instances（2025 challenge test_instances.csv）
- 协议：10 个任务 $\times$ 3 轮 $\times$ 1 实例 = 30 条 rollout  
- 孤立评测：validation split 的干净 snapshot，VLM 验证 + 人工复核
- 组合评测：live VLA 执行，每个技能从前一个技能的终端状态启动
- 进度评分：人工从视频评分，按完成的参考技能序列比例计算（保守估计）

**验证器审计**：
- 盲审 2 名标注员
- 21 次 VLM 标记的失败中，20 次被判定为真实失败
- 过严格率：0.05（即 5% 的失败判定可能过于保守）

### 6.1 隐含假设 (Hidden Assumptions)

1. **技能库覆盖足够**：假设 9 种技能类型能覆盖 BEHAVIOR-1K 的所有任务需求，但未验证新技能类型的泛化能力
2. **VLM 验证器足够可靠**：20/21 的审计一致率看似高，但样本量极小（21 次），且只验证了二元失败判定，未验证失败类别标签的准确性
3. **恢复策略充分**：当前恢复主要是 re-navigate + retry，但缺少更丰富的恢复模式（如改变视角、更换抓取策略）
4. **仿真到现实的迁移**：所有实验在 OmniGibson 仿真中完成，未讨论 sim2real gap
5. **步数预算合理**：B_s 按技能类型预设，但未说明如何确定最优预算值
