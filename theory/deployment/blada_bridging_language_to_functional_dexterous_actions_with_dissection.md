## 1. 核心架构/方法总览 (Overview / Architecture)

| 模块 | 输入 | 输出 | 频率/时序 | 训练/推理 |

| TriLocation (3D 定位) | 多视角 RGB-D + S 中的 (g^a, g^r, τ, κ) | 三个功能关键点 P={p1, p2, p3} | 每场景重建一次 | 需训练 (MLP+3DGS 蒸馏) |
| KGT3D+ (执行) | P + (g^t, g^f) | 手腕位姿 (R,T) + 关节角 J + 力 F | 每次抓取 | 确定性计算 (F2F 查找表) |

**端到端流程**：
```

                ↓                        ↓                        ↓
           语义锚点                 几何约束                  物理可执行
```

### 1.2 关键机制 (Key Mechanism)

**KLP 模块**：将开放词汇指令解析为六元组：
- g^a (grasp affordance): 可用区域的空间可达性
- g^r (role assignment): 各手指接触时的功能角色
- g^t (grasp type): 抓握手势/类型，对应关节角预定义值
- g^f (force level): 交互力度等级
- τ (tool topology): 工具拓扑先验 (rod/handle/knob/surface 四类)
- κ (task intent): 任务意图先验 (press/click/open/hold 四类)

**TriLocation 模块**：
- 用 3DGS 构建连续场景表示
- HSE (Hierarchical Semantic Extraction) 解决语义漂移：对象级 vs 部件级特征解耦
- 三角形功能点定位：p1 (功能指尖), p2 (小指侧支撑), p3 (手腕支撑)
- 任务 - 工具局部坐标系约束：确保不同视角下三点几何关系稳定

**KGT3D+ 模块**：
- 从三点构建右手坐标系：z→=(p1-p3)/‖p1-p3‖, y→=((p2-p3)×z→)/‖(p2-p3)×z→‖, x→=y→×z→
- 手腕位姿：R=[x→ y→ z→], T=p3
- 从 F2F 知识库查表得关节角 J 和力 F

⚡ **Eureka Moment**：用 3D 高斯场中的**三角形关键点结构**作为语言 - 几何 - 控制的统一中间表示——既保持语义可解释性，又直接映射到物理可执行的位姿和手指命令。

## 2. 数学核心 (Math Core)

📌 **Napkin Formula**（一行抓住本质）：
```
G, P = M(L, Ω)  其中 S=KLP(L,Prompt), P=TriLocation(Ω,S), (R,T,J,F)=KGT3D+(P,g^t,g^f)
```

**KLP 输出六元组**：
```
S = {g^a, g^r, g^t, g^f, τ, κ} = KLP(L, P)
```
变量说明：
- g^a: grasp affordance (可用区域)
- g^r: role assignment (手指角色)
- g^t: grasp type (手势类型)
- g^f: force level (力度)
- τ: tool topology ∈ {rod, handle, knob, surface}
- κ: task intent ∈ {press, click, open, hold}

**3DGS 特征渲染**：
```
F^ = Σ_{i=1}^{N} f_i · α_i · Π_{j=1}^{i-1} (1 - α_j)
```
变量说明：
- f_i ∈ R^d: 第 i 个高斯原语的潜在特征
- α_i: 不透明度
- F^: 渲染的潜在特征

**上下文感知裁剪**（解决语义漂移）：
```
B'_p = [x1 - γ·w, y1 - γ·h, x2 + γ·w, y2 + γ·h]
```
变量说明：
- B_p = [x1, y1, x2, y2]: 部件边界框
- γ: 填充比例 (超参数)
- w, h: B_p 的宽度和高度

**三点坐标计算**（局部坐标系中）：
```
p2 = p1 + R · [0, -L12·sin(A1), -L12·cos(A1)]^T
p3 = p1 + R · [0, 0, -L13]^T
```
变量说明：
- p1: 语义锚点 (功能指尖接触点)
- L12, L13: 模板提供的边长
- A1: p2 与 p3 的夹角
- R ∈ R^{3×3}: 由任务 - 工具规则确定的旋转矩阵

**手腕位姿构建**：
```
z→ = (p1 - p3) / ‖p1 - p3‖
y→ = ((p2 - p3) × z→) / ‖(p2 - p3) × z→‖
x→ = y→ × z→
R = [x→  y→  z→],  T = p3
```

**关节与力查表**：
```
J, F = F2F(g^t, g^f)
```

> 符号与本文/相关文档保持一致：上标 a/r/t/f 分别对应 affordance/role/type/force；τ/κ 为希腊字母表示拓扑和意图先验。

## 3. 带数字走一遍：玩具例子 (Worked Example)

**场景**：指令 "Handover me the drill" (把电钻递给我)

**Step 1: KLP 解析**
```
输入 L = "Handover me the drill"
输出 S = {
  g^a = "handle region",      # 可用区域：手柄
  g^r = "thumb-index grip",   # 手指角色：拇指 - 食指抓握
  g^t = "power_grasp",        # 手势：强力抓握
  g^f = "medium",             # 力度：中等
  τ = τ_handle,               # 拓扑：侧向手柄
  κ = hold                    # 意图：持握
}
```

**Step 2: TriLocation 定位**
假设 3DGS 场重建后，CLIP 相似度阈值 δ=0.7，找到高斯簇质心：
```
p1 = (0.15, 0.32, 0.48)  # 手柄功能接触点 (食指)
```
从手模板查得边长 L12=0.08m, L13=0.12m, 夹角 A1=30°。
局部坐标系由 τ_handle + κ=hold 确定：
```
z^ = 径向方向 (从手柄中心向外)
y^ = 手柄轴线方向
x^ = y^ × z^
```
计算 p2, p3：
```
p2 = p1 + R · [0, -0.08·sin(30°), -0.08·cos(30°)]^T
   = p1 + R · [0, -0.04, -0.069]^T
   ≈ (0.15, 0.28, 0.41)  # 小指侧支撑点

p3 = p1 + R · [0, 0, -0.12]^T
   ≈ (0.15, 0.32, 0.36)  # 手腕支撑点
```

**Step 3: KGT3D+ 执行**
构建手腕坐标系：
```
z→ = (p1 - p3) / ‖p1 - p3‖ = (0, 0, 0.12) / 0.12 = (0, 0, 1)
y→ = ((p2 - p3) × z→) / ‖...‖ ≈ (0, -1, 0)  # 归一化后
x→ = y→ × z→ = (-1, 0, 0)

R = [[-1,  0,  0],
     [ 0, -1,  0],
     [ 0,  0,  1]]
T = p3 = (0.15, 0.32, 0.36)
```
查 F2F 表得 power_grasp + medium force 对应的关节角 J 和力 F，发送给 Inspire Hand 执行。

**闭环验证**：三点构成的三角形边长与模板一致，手腕位姿确保手掌朝向手柄，手指预设为强力抓握姿态——物理可执行。

## 4. 工程视角 (Engineering View)

| 工程指标 | 数值/约束 | 含义 |
|----------|-----------|------|
| 3DGS 重建时间 | ~数分钟 (RTX 3090) | 每场景一次性开销，不适合高动态环境 |
| TriLocation 训练 | 3000 iterations | 论文默认设置，可增加但收益递减 |
| KLP 推理延迟 | ~1-3s (取决于 LLM) | 零样本，无训练开销 |
| KGT3D+ 计算 | <10ms | 确定性几何计算 + 查表，实时 |
| 关键点定位精度 | LSR 68.75% (阈值内) | 3D 坐标偏差在预定义阈值内算成功 |
| 功能抓取成功率 | FSR 未明确给出 (需看 Table V) | 物理试验 100 次的成功比例 |
| 内存占用 | 3DGS 场 + 特征 ≈ 数百 MB | 取决于场景复杂度 |
| 量化误差 | 未讨论 | 潜在风险：低精度推理可能影响定位 |

**部署约束**：
- 需多视角 RGB-D 输入 (Intel RealSense D435i)
- 需 Franka Emika 机械臂 + Inspire Hand 灵巧手
- 需 world2base 手眼标定矩阵
- 3DGS 重建是离线/准离线过程，不适合毫秒级响应场景

**Trade-off 分析**：
- **精度 vs 速度**：3DGS 重建质量高但慢；若用稀疏点云会更快但定位精度下降
- **泛化 vs 特化**：零样本设计牺牲了任务最优性能，换取跨任务迁移能力
- **可解释 vs 端到端**：模块化架构便于调试和干预，但误差会逐级累积

**评测指标**：
| 指标 | 定义 | 用途 |
|------|------|------|

### 6.2 不能做什么 (Failure Modes)

| 失败模式 | 原因 | 缓解方案 |
|----------|------|----------|
| 动态场景 | 3DGS 重建是静态的 | 需定期重重建或改用动态 3DGS |
| 未见物体类别 | 零样本但依赖 CLIP 语义 | 扩展 F2F 知识库，增加示例 |
| 遮挡严重 | 多视角重建质量下降 | 增加相机数量或主动视角规划 |
| 快速交互 | 重建 + 推理延迟秒级 | 不适用于毫秒级闭环控制 |
| 非桌面场景 | 实验仅在桌面操作验证 | 需验证移动/双臂/人形场景 |

### 6.3 隐含假设 (Hidden Assumptions)

**X-Ray 批判视角**：
1. **物体静止假设**：3DGS 重建期间物体不能移动，否则场不一致
2. **多视角可获取**：默认能从多个角度拍摄 RGB-D，实际中可能受限
3. **CLIP 语义覆盖**：假设 CLIP 能理解所有工具部件语义，长尾类别可能失效
4. **F2F 知识库完备**：预设手势和力的组合需人工定义，新抓握类型需扩展
5. **手眼标定精确**：world2base 矩阵误差会直接传递到执行精度
