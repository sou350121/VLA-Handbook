## 1. 核心架构/方法总览 (Overview / Architecture)

### 1.1 系统对比概览 (System Component Comparison)

| 维度 | 传统 RPA | 端到端 VLA | 本文混合架构 |
|------|----------|------------|-------------|
| 执行延迟 | <50ms | 2-10s/次 | <50ms（常规）/ ~10s（漂移恢复） |
| 确定性 | 强（硬编码坐标） | 弱（概率输出） | 混合：System 1 确定 + System 2 概率 |
| UI 漂移鲁棒性 | 零（坐标偏移即失效） | 强（语义理解） | 强（System 1 失效时触发 System 2） |
| 推理成本 | 极低（本地 CPU） | 高（API/大模型） | 极低（均摊） |
| 可解释性 | 高（脚本可读） | 低（黑盒） | 高（场景图可查询） |
| 维护成本 | UI 变时高 | 低 | 中（需维护锚点缓存） |
| 安全保证 | 无（可能误操作） | 中（可能幻觉） | 高（置信度阈值 + 场景图验证） |

### 1.2 关键机制 (Key Mechanism)

论文提出三层异步控制回路，由四个架构模式实现：

**回路 1 — 反射回路（Reflex Loop, System 1）**
- 使用缓存的视觉锚点（模板/特征嵌入）进行快速 UI 定位
- 延迟 <50ms，确定性执行
- 当匹配置信度低于阈值 τ 时自动抑制执行并触发升级

**回路 2 — 结构回路（Structural Loop）**
- 将扁平的感知输出聚合为层级化 UI 表示
- 使用格式塔分组原则（包含、对齐）推断树状结构
- 提供相对寻址，使布局平移不影响操作正确性

**回路 3 — 监督回路（Supervisor Loop, System 2）**
- VLA 模型作为概率监督者，仅在感知失败或 UI 漂移时激活
- 分析新 UI 状态，更新 System 1 的视觉模板缓存
- 构建可查询的语义场景图用于安全验证

⚡ **Eureka Moment**: VLA 不应该每次都做决策——它应该只在反射失败时被调用，把"昂贵的语义推理"摊销到"廉价的本地反射"上。对于一个 UI 稳定的企业 ERP 系统，P(Drift) ≈ 1%，这意味着 99% 的操作不需要 VLA。

## 2. 数学核心 (Math Core)

📌 **Napkin Formula**（一行抓住本质）：

```
C_avg = C_reflex + (P_drift × C_supervisor)
```

**目标**: 最小化每次操作的平均成本，使得在保持 VLA 语义弹性的同时，经济上可行地用于高频批处理。

**变量说明**:

| 符号 | 含义 | 论文中的典型值 |
|------|------|---------------|
| C_avg | 每次操作的平均成本/延迟 | 目标 <1s |
| C_reflex | 反射回路成本（模板匹配） | <50ms |
| P_drift | UI 漂移概率（布局变化/样式变更） | ~1% |
| C_supervisor | VLA 监督者成本（推理+网络往返） | ~10s |

**直觉**: 当 P_drift 很低时（企业 ERP UI 通常数月不变），C_avg ≈ C_reflex。VLA 的昂贵推理被摊销到大量常规操作中。即使 C_supervisor = 10s，只要 P_drift = 0.01，均摊增量仅为 0.1s。

**延迟等效公式**:

```
T_avg = T_reflex + (P_drift × T_supervisor)
     ≈ 50ms + (0.01 × 10,000ms)
     = 50ms + 100ms
     = 150ms  << 10,000ms (纯 VLA)
```

> 符号与本文保持一致。P_drift 的具体值取决于目标系统的 UI 稳定性——频繁更新的 SaaS 应用可能 P_drift 更高，而传统桌面 ERP 则更低。

## 3. 带数字走一遍：玩具例子 (Worked Example)

假设场景：批处理 1000 张发票审批，每张需要定位"Submit"按钮并点击。

**场景设定**:
- 前 999 张发票：UI 稳定，"Submit"按钮位置不变
- 第 1000 张发票处理前：供应商更新，按钮右移 50px，颜色从蓝变绿，原位置出现"Delete"按钮

**三种架构的对比执行**:

| 架构 | 第 1-999 张 | 第 1000 张 | 总耗时 | 安全结果 |
|------|------------|-----------|--------|---------|
| RPA | 50ms × 999 = 49.95s | 50ms（点 Delete！） | ~50s | ❌ 灾难性失败 |
| 端到端 VLA | 10s × 999 = 9990s | 10s（正确识别 Submit） | ~10000s (2.8h) | ✅ 正确但极慢 |
| 混合架构 | 50ms × 999 = 49.95s | 50ms(失败) + 10s(VLA修复) + 50ms(执行) = 10.1s | ~60s | ✅ 正确且快 |

**均摊计算验证**:

```
P_drift = 1/1000 = 0.001
C_avg = 50ms + (0.001 × 10,000ms) = 50ms + 10ms = 60ms
总耗时 = 60ms × 1000 = 60s
```

关键洞察：混合架构的总耗时（60s）仅比纯 RPA（50s）多 20%，但获得了 VLA 级别的弹性，同时比纯 VLA（2.8 小时）快了 166 倍。

## 4. 工程视角 (Engineering View)

### 4.1 模块边界与接口设计

| 组件 | 输入 | 输出 | 频率 | 部署位置 |
|------|------|------|------|---------|
| UI 检测器 | 屏幕截图 | 边界框列表 + 置信度 | 每帧 | 本地（轻量模型） |
| OCR 引擎 | 屏幕截图 | 文本区域 + 内容 | 每帧 | 本地（Tesseract 等） |
| 感知仲裁器 | 检测框 + OCR 文本 | 融合后的 affordance 列表 | 每帧 | 本地 |
| 视觉锚点缓存 | affordance 列表 | 匹配结果 + 置信度 | 每操作 | 本地内存 |
| 布局解析器 | affordance 列表 | 层级 UI 树 | 每帧 | 本地 |
| 场景图构建器 | UI 树 | 语义场景图（图数据结构） | 每帧 | 本地 |
| VLA 监督者 | 截图 + 自然语言指令 | 新锚点 + 坐标 + 策略 | 仅漂移时 | 云端/API |

### 4.2 关键 Trade-off

**置信度阈值 τ 的选择**:
- τ 过高（如 0.99）：频繁触发 VLA，延迟上升，成本增加
- τ 过低（如 0.5）：可能误触发操作，安全风险
- 论文建议 τ < 0.9 作为安全阈值（§V-B），实际应根据任务风险调整——高危操作（删除/转账）应设更高阈值

**缓存更新策略**:
- 全量更新：VLA 每次重建所有锚点（安全但慢）
- 增量更新：仅更新失效锚点（快但可能遗漏级联漂移）
- 论文暗示增量更新：VLA "updates the first layer's visual template cache"（§V-B）

**内存与存储**:
- 视觉锚点缓存大小取决于 UI 复杂度：一个典型 ERP 表单可能有 20-50 个可交互元素
- 每个锚点（模板图像 + 特征向量）约 1-5KB，总缓存 <1MB，完全可放入内存

### 4.3 部署约束

- **网络依赖**: VLA 监督者需要云端 API，反射回路完全本地
- **断网容错**: 反射回路可独立工作，但无法处理 UI 漂移
- **多实例扩展**: 每个 Agent 实例维护独立缓存，无共享状态需求

## 6. 能力与失败模式 (Capabilities & Failure Modes)

### 6.1 能做什么

| 能力 | 说明 | 依赖条件 |
|------|------|---------|
| 高频批处理 | 均摊延迟 <1s/操作 | UI 稳定（低 P_drift） |
| UI 漂移自适应 | 自动检测并恢复 | VLA 监督者可调用 |
| 安全保证 | 置信度阈值防止误操作 | τ 设置合理 |
| 可审计性 | 场景图可查询，决策可追溯 | 场景图正确构建 |
| 跨平台通用 | 模式独立于具体 VLA 模型 | 有可用的 VLA 和检测器 |

### 6.2 不能做什么（失败模式）

| 失败模式 | 原因 | 缓解 |
|---------|------|------|
| 高频 UI 变化场景 | P_drift 高时均摊成本上升 | 不适用或需更轻量的 System 2 |
| 复杂手势操作 | 反射回路仅支持点击/输入等基元 | 扩展 System 1 动作空间 |
| 多窗口/多显示器 | 场景图目前假设单窗口 | 扩展场景图为多窗口图 |
| VLA 幻觉传播 | System 2 的错误锚点会污染 System 1 | 加入锚点验证机制 |
| 动态内容（视频/动画） | 模板匹配对动态内容失效 | 结合时序特征检测 |

### 6.3 隐含假设 (Hidden Assumptions)

1. **UI 变化是稀疏的**：论文假设 P_drift 很低（~1%），这在传统 ERP 中成立，但在频繁更新的 SaaS 产品中可能不成立。如果 UI 每天变化，均摊成本将趋近于纯 VLA。

2. **VLA 监督者总是正确的**：论文假设 System 2 能正确识别新 UI 元素并生成正确的锚点。但如果 VLA 产生幻觉（如将 Cancel 误认为 Submit），错误的锚点会被缓存并用于后续操作，导致系统性错误。

3. **单用户单会话**：场景图假设单一用户视角。多用户协作场景（如共享文档、实时编辑）下的场景图一致性未讨论。

4. **检测器足够可靠**：Hybrid Affordance Integration 假设 UI 检测器和 OCR 能覆盖绝大多数 UI 元素。对于自定义渲染的非标准控件（如 Canvas 绘制的图表），检测器可能完全失效。

5. **GUI 是离散的**：模式语言假设 UI 由可分离的控件组成。对于全屏游戏、3D 应用或纯 Canvas 应用，"控件"概念本身不存在。
