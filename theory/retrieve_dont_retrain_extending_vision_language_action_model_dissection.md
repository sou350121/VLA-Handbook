## 1. 核心架构/方法总览 (Overview / Architecture)

### 1.1 系统对比概览 (System Component Comparison)

| 组件 | 训练时 | 部署时 | 说明 |
|------|--------|--------|------|
| 检索池 D_pool | 池端训练演示 D_train_pool | 新任务池端演示 D_test_pool | 可动态扩展，无需改参数 |
| 查询端观测 s_t^query | 配对演示中的目标端状态 | 实时传感器观测 | 策略唯一在线输入 |
| 检索模块 | 每步检索最近邻池端 chunk | 同左，池子可增长 | 复合特征距离（语言+物体位姿+本体感知+视觉） |
| 策略 π_θ | 在配对数据上训练一次 | 冻结，仅推理 | 输出残差 Δa，非绝对动作 |
| 损失函数 | L = λ·L_act + L_state（动作+未来图像联合） | N/A | L_state 仅在 WAM 中存在 |

### 1.2 关键机制 (Key Mechanism)

ReCAP 的核心机制由三个齿轮组成：

1. **检索条件化（Retrieval Conditioning）**：每控制步从池中检索一个状态-动作片段 (s_{t':t'+H}^pool, a_{t':t'+H}^pool)，与当前查询观测 s_t^query 一起编码为干净潜变量帧，沿时间轴拼接后送入 WAM backbone。语言指令通过 cross-attention 注入。

2. **残差动作参数化（Residual Action）**：策略不直接预测绝对动作，而是预测相对于检索动作的修正量 Δa。公式：a_hat^query = a_retrieved^pool + Δa。这迫使策略只学习"目标端与池端执行方式的差异"——即 embodiment gap。

3. **WAM 未来图像一致性（Future-Image Consistency）**：Cosmos Policy 同时预测未来动作和未来图像。未来图像预测对检索轨迹施加视觉一致性约束——如果检索的动作片段与场景演化矛盾，图像预测会惩罚它。这是 WAM 比纯动作策略（如 π0.5）从检索中获益更多的根本原因。

⚡ **Eureka Moment**：把"适配新任务"从参数空间（微调）搬到数据空间（检索池扩展）——策略冻结，知识外化为可搜索的演示库。

## 2. 数学核心 (Math Core)

📌 **Napkin Formula**（一行抓住本质）：

```
a_hat_query = a_retrieved_pool + Δa_θ(s_t_query, retrieved_chunk)
```

检索提供粗粒度运动先验，策略只学 embodiment-specific 修正。

**目标**：在策略冻结的前提下，让目标端机器人执行训练时未见过的任务。

**核心方程**：

```
L(θ) = λ · L_act(a_hat_query, a_query) + L_state(s_hat_query, s_query)
```

其中：
- L_act：动作流匹配损失（flow-matching loss），监督预测动作与真实动作
- L_state：未来图像流匹配损失，监督预测未来帧与真实未来帧
- λ：权重系数（论文未给出具体值）

**变量说明**：

| 符号 | 含义 |
|------|------|
| θ | 策略参数（训练后冻结） |
| s_t^query | t 时刻目标端观测状态 |
| s_t^pool | t 时刻池端观测状态 |
| a_t^query | 目标端动作（SE(3) 末端执行器位姿 + 夹爪信号） |
| a_t^pool | 池端动作（同上，共享动作空间） |
| H | 动作 chunk 长度 |
| t' | 检索到的池端最近邻索引 |
| Δa | 残差动作修正 |

> 符号与本文保持一致：上标 query/pool 区分两端，上标 hat 表示预测值。

**直觉**：联合训练 L_act + L_state 产生"与场景演化一致的动作"。如果检索的动作片段会导致不合理的未来图像（如穿过障碍物），L_state 会惩罚它。这就是为什么去掉 L_state 后性能从 34.9% 掉到 27.4%（与纯动作策略 π0.5 的 25.1% 相当）。

## 3. 带数字走一遍：玩具例子 (Worked Example)

以 PushT 实验为例，理解检索如何工作。

**训练设置**：
- 目标端：三角形推手（triangle）
- 池端：圆盘推手（disc）
- 训练任务：±45° 目标角，各 100 对配对演示
- 测试任务：-60° 到 +60° 共 9 个角度，其中 7 个未见

**推理过程走一遍（目标角 = 0°，训练时未见）**：

```
Step 1: 当前观测 s_t^query = 三角形在 (x=2, y=3), T块在 (x=5, y=5)
Step 2: 检索 → 在池中找最接近的池端状态
        → 找到 t' = disc 在 goal_angle=0° 的演示中的某帧
        → 检索 chunk: (s_{t':t'+H}^disc, a_{t':t'+H}^disc)
Step 3: 将检索 chunk 编码为潜变量帧，与 s_t^query 拼接
Step 4: WAM 前向传播 → 输出:
        a_hat_query = a_retrieved_disc + Δa
        假设 a_retrieved_disc = [vx=0.5, vy=0.3, ω=0.01]
        假设 Δa = [vx=0.02, vy=-0.05, ω=-0.003]  ← 三角形特有的修正
        → a_hat_query = [vx=0.52, vy=0.25, ω=0.007]
Step 5: 执行 a_hat_query，进入下一步
```

**关键观察**：
- 即使池中还没有精确匹配 0° 的演示（比如池子只有 ±5° 分辨率），策略也能通过邻近演示插值泛化
- PushT 实验中，每个角度在匹配池演示加入前就达到了大部分最终成功率——证明策略在插值，而非 memorize

**池扩展效果（PushT unseen angles 平均成功率）**：

| 池大小 | 成功率 | 增量 |
|--------|--------|------|
| 无检索（baseline） | 6.0% | — |
| 5° 分辨率 | ~15% | +9% |
| 15° 分辨率 | ~22% | +7% |
| 全池（5° 分辨率, [-60°, +60°]） | 34.9% | +12.9% |

## 4. 工程视角 (Engineering View)

| 维度 | 传统微调范式 | ReCAP 检索范式 | 工程含义 |
|------|-------------|---------------|---------|
| 每任务数据成本 | ~18× 遥操作收集 | 1× 人手演示（轻量 tracker） | 数据成本降低 18 倍 |
| 每任务计算成本 | ~24 GPU 小时（Cosmos） | 0 GPU 小时（检索仅 CPU） | 部署成本趋近于零 |
| 推理延迟 | 单次前向传播 | 检索 + 单次前向传播 | 增加检索开销（向量搜索），但远低于训练 |
| 存储需求 | 模型权重 | 模型权重 + 检索池数据库 | 池随任务线性增长，需管理索引 |
| 泛化机制 | 参数内化 | 参数冻结 + 数据外化 | 类似 RAG：知识在数据库，不在权重 |
| 时间尺度鲁棒性 | 训练时隐式学习 | 残差对速度/时序差异敏感 | 大 chunk 下误差累积是已知风险 |

**部署约束**：
- 检索每控制步执行一次 → 需要低延迟向量检索（FAISS 级别）
- 池端演示必须已 lift 到 SE(3) 状态-动作空间 → 纯视频不能直接用
- 目标端和池端共享末端执行器动作空间 → 结构性差异（灵巧手 vs 平行夹爪）需要额外接口

### 6.1 隐含假设 (Hidden Assumptions)

1. **共享动作空间假设**：论文假设目标端和池端都使用 SE(3) 末端执行器位姿 + 夹爪信号。如果一端是 7-DOF 灵巧手，另一端是 2-finger 夹爪，残差 Δa 的维度都不匹配。作者承认这是局限，但未提供解决方案。

2. **检索质量假设**：复合检索描述子 ψ0 依赖 SAM 3 物体检测 + DINOv3 视觉特征 + 语言嵌入。如果 SAM 3 在新场景中检测失败（如透明物体、遮挡），检索质量会下降。论文未在检索失败情况下做 ablation。

3. **时间尺度对齐假设**：残差公式 a_hat = a_pool + Δa 隐含假设池端和目标端的执行速度相近。如果人手演示 5 秒完成，机器人需要 15 秒，残差会累积误差。论文在 limitations 中提到但未量化。

4. **池演示覆盖假设**：池必须包含语义相似的任务演示。如果新任务完全超出池的语义范围（如池里全是"推"任务，新任务是"拧"），检索无意义。这本质上是 OOD 泛化问题，论文未讨论。

## 7. 与相关工作对比 (Comparison)

| 方法 | 新任务适配方式 | 是否需要训练 | 跨端能力 | 适用场景 |
|------|---------------|-------------|---------|---------|
| Per-task fine-tuning | 收集目标端演示 + 微调 | 是（~24 GPUh） | 有限 | 单端多任务 |
| Co-training | 联合训练目标+池端数据 | 是（一次性） | 是 | 已知端集合 |
| R+X | 直接执行人手视频 | 否 | 是 | 人在环 |
| MimicDroid | 条件于人手 prompt | 是 | 是 | 需手动选择 |
| STRAP | DTW 匹配子轨迹 + 训练 | 是（测试时） | 是 | 单端 |
| **ReCAP（本文）** | **检索池扩展** | **否** | **是** | **跨端新任务** |

**面试 Tip**：当被问到"ReCAP 和 RAG 有什么区别"时，回答：RAG 检索的是文本知识块，ReCAP 检索的是状态-动作轨迹片段；RAG 的生成器独立于检索内容，ReCAP 的策略以残差方式显式依赖检索动作——检索不是补充，是动作的骨架。
