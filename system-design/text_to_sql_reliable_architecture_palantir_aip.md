# Text-to-SQL 的可靠架构：Palantir 式“语义层 + 工具化”解法

> **定位**：把“问数”从“模型能力问题”升级为“系统工程问题”，面向企业级可信与可审计。  
> **口径说明**：以下为用户提供的行业解读与实践共识整理，**非官方白皮书**，关键细节需二次核验。

---

## 1. 为什么直接让 LLM 写 SQL 会出灾难？
典型失败模式：
- **字段对不上**：schema 太复杂，模型连表选错。  
- **SQL 能跑但结果错**：口径歧义、过滤条件缺失。  
- **幻觉数字**：不查库直接编。  

结论：**Text-to-SQL 的难点不在“能写 SQL”，而在“能保证正确性”**。

---

## 2. Palantir 式核心原则：LLM 不“回忆”，只“查询”
业界对 Palantir AIP 的理解可以抽象为一句话：

> **让 LLM 做“编排器”，让确定性工具做“执行器”。**

他们强调的准确性公式（用户口径）：

```
准确性 = 高质量本体 (Data) + 确定性工具 (Logic) + 全链路溯源 (Audit)
```

### 2.1 本体 (Ontology) 是“唯一真理”
- 不把私有数据直接灌入 LLM  
- 先构建语义对象层（工厂/订单/客户），再映射到表  
- 避免“表结构驱动的查询逻辑”

### 2.2 LLM 只负责“按按钮”
从“直接写 SQL”转为“调用工具”：
- LLM 识别意图 → 生成工具调用  
- 工具执行 → 返回确定性结果  

示意：
```
用户：查中国区销量
LLM：sum_sales(region="China")
系统：工具执行 + 结果返回
```

### 2.3 结果必须可追溯 (Audit)
- 可见执行 DAG  
- 可追溯到行级数据  
- 结果可解释、可复盘

---

## 3. 业界共识：高容错“问数”五件套

1) **语义层 (Semantic Layer)**
- 把“开放写 SQL”变成“封闭选指标”  
- 典型实现：Metric Store / Headless BI

2) **Schema Linking（上下文绑定）**
- 列值样本与同义词映射  
- 业务术语表（“大客户”/“活跃用户”定义）

3) **慢思考 + 自纠错**
- CoT / 多步推理  
- SQL 执行报错回传 → 自动修复  
- 空结果 → 放宽条件重试

4) **交互式澄清**
低置信度时必须反问：
- “最好”是指销量还是利润？  
- 时间范围是否明确？

5) **确定性执行环境**
复杂逻辑可转为 **Python Sandbox** 执行：
- 更易调试  
- 可单元测试  

---

## 4. 可落地参考架构（简化版）
```
用户问题
  │
  ├─ 意图解析 (LLM)
  │
  ├─ 语义层映射 (Ontology / Metric Store)
  │
  ├─ 工具调用 (SQL / Python / BI API)
  │
  ├─ 执行与校验 (Deterministic)
  │
  └─ 审计与解释 (DAG + Row-level Trace)
```

---

## 5. 关键验收清单
- [ ] LLM 是否只负责“编排”，而非直接计算？  
- [ ] 是否有统一语义层与口径控制？  
- [ ] 结果是否可追溯到行级？  
- [ ] 低置信度是否能自动反问？  
- [ ] 复杂逻辑是否可迁移到 Python Sandbox？

---

## 6. 风险与边界
- 没有语义层，Text-to-SQL 准确率难上 80%  
- 只做 RAG 不够：必须有工具调用与审计链路  
- 业务口径变化必须能快速回写语义层
