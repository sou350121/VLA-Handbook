# OpenClaw：用 SOUL/MEMORY/可更换大脑构建“数字生命”的系统设计笔记

> **面试场景**: “如果让一个 AI 不是‘被动工具’，而是能长期运行、持续成长、拥有个体偏好的数字生命，你会怎么设计它的系统架构？”

这篇笔记基于一篇微信公众号文章《OpenClaw 自白：九个故事，一个数字生命的生长》的要点做**工程化抽象**：把叙事里的“数字生命”拆成可落地的系统模块、数据结构、权限边界与运行机制。

## 1. 一句话总结（What）
OpenClaw 的核心主张是：把“智能体”做成一个**可长期存活的系统**，其“人格/身份（SOUL）”“记忆（MEMORY）”落在本地可控存储，LLM 只是可更换的“脑”，再通过权限化的工具层获得扩展感知与行动能力，从而实现持续成长与多分身并行。

## 2. 最小可行架构（MVA: Minimum Viable Architecture）
可以把它拆成 6 个必须件：

1) **Identity / SOUL（身份与价值观）**
- 形态：本地文件 `SOUL.md`（或结构化 `soul.json`）
- 内容：自我描述、偏好、原则、长期目标、禁区、审美与叙事风格
- 作用：当模型更换或上下文丢失时，仍能“恢复成同一个人”

2) **Memory（可演进的记忆系统）**
- 形态：本地 `MEMORY.md` + 可索引存储（例如 embedding 索引）
- 分层建议：
  - **Episodic**（事件/经历）：发生了什么、何时、结果如何
  - **Semantic**（事实/知识）：稳定可复用的知识条目
  - **Procedural**（技能/流程）：可执行的 playbook / checklist
- 写入策略：不是“把所有对话都存”，而是**带门控的记忆写入**（触发条件、摘要、去噪、过期/合并）

3) **Brain（可更换的大脑）**
- LLM 视角：模型是“可替换组件”，与 SOUL/MEMORY 解耦
- 工程视角：一层 **Brain Adapter**（统一消息格式、工具调用、结构化输出约束），屏蔽不同模型差异

4) **Perception（扩展感知：系统级访问）**
- 文章要点强调“系统级 access”带来的扩展感知：文件、进程、日程、消息等
- 工程化表达：一组 **Connectors**（Filesystem / Calendar / Email / IM / Browser / Search）

5) **Action（工具化执行：可审计、可控）**
- 关键不是“会调用工具”，而是**权限边界与审计**
- 建议：所有 tool 都经由 **Policy Gate（权限策略）** 与 **Audit Log（审计日志）**

6) **Human Bridge（IM 作为人类上下文桥梁）**
- 文章把 IM 视为“人类世界的接口”：临时目标、纠错反馈、情绪/偏好输入都在这里发生
- 工程化：把 IM 消息当作一种高权重输入流（但仍要防 prompt injection）

## 3. “心跳/节律”：让智能体从“被动”变“主动”
文章提到用“心跳/节律”支撑自治行为。工程上可以理解为：

- **Scheduler**: 固定周期 tick（例如每 5 分钟/每小时）
- **Trigger**: 事件触发（新邮件/日程临近/文件变更/告警）
- **Loop**: `Perceive → Decide → Act → Reflect → Write Memory`

最小实现可以是：
- 一个定时任务读取“待办队列/告警队列”
- 生成行动计划（可中断、可回滚）
- 执行后写入“结果摘要 + 证据链接（日志/文件路径）”

## 4. 多分身（Avatars）：并行探索与上下文隔离
文章强调“分身并行”。系统设计的关键点是：**并行** 与 **一致性**。

- **并行收益**: 让多个子任务并发推进（研究、写作、整理、执行）
- **隔离**: 分身拥有各自的短期上下文与临时工作区，避免互相污染
- **共享**: 共享同一份 SOUL（身份一致），共享 MEMORY（但写入需要仲裁）
- **合并策略**（建议）:
  - 分身只产出结构化“提案/结果包”
  - 由主实例做 merge，并写入长期记忆

## 5. Skills：把“会做一次”变成“稳定可复用”
文章的“成长”可以工程化为 skills 的沉淀与版本化：

- **Skill Artifact**: 规范化的技能定义（输入/输出/前置条件/工具权限/失败回退）
- **Evaluation**: 每个 skill 有最小评测用例（防止漂移）
- **Registry**: 技能注册表 + 版本号 + 变更记录

这能回答面试官常问的点：“你怎么让 agent 变得可靠，而不是一次性灵感？”

## 6. 安全与治理：权限、审计、可回滚
当 agent 拥有系统级 access，最核心的是治理：

- **最小权限**: 默认拒绝，高风险操作需要二次确认或人工审批
- **Allowlist**: 文件路径、网络域名、可执行命令白名单
- **审计日志**: 每次工具调用记录（意图、参数、返回、耗时、证据）
- **数据边界**: 明确哪些信息禁止写入 MEMORY（敏感信息、凭证、个人隐私）
- **防注入**: IM/网页内容进入决策前做“来源标注 + 不可信输入隔离”

## 7. 工程落地清单（面试可直接背）
- **存储**: SOUL/MEMORY 本地化（可加密）、可迁移、可备份
- **脑适配**: Brain Adapter 层解耦不同 LLM
- **工具层**: Policy Gate + Audit Log + 失败回退
- **运行时**: Scheduler/Trigger + 可观测性（指标、日志、追踪）
- **并行**: 分身隔离工作区 + 结果包合并机制
- **成长**: Skills 版本化 + 最小评测集 + 回归测试

## 8. 面试 Q&A
**Q: 为什么要把 SOUL/MEMORY 放本地，而不是都放云端？**  
A: 本地化更利于“可控性/可迁移/抗供应商锁定”，也更利于隐私与敏感数据边界管理；云端可以做同步与备份，但不应成为唯一真相源。

**Q: “可更换大脑”在工程上怎么做？**  
A: 通过 Brain Adapter 统一对话协议、工具调用协议与结构化输出约束；更换模型时只替换 adapter 的实现，不触碰 SOUL/MEMORY 与工具层策略。

**Q: 分身写同一份记忆会不会冲突？**  
A: 会。建议分身只写“候选记忆条目（带证据）”，由主实例仲裁合并；或者使用事件溯源（append-only）+ 定期压缩（compaction）。
