# 数据失效模式 F1-F6（Debug 真机必备）

> 🧠 作者提出的分类法 · 参考 [VLA 数据工程指南 §3.5](../theory/foundation/vla_data_engineering_guide.md)
> **使用原则**：F1-F6可能伴随低或正常的训练Loss；不能凭loss排除这些失效，仍需结合输入核查与闭环对照。

> **诊断边界（2026-11-08）**：下列分类用于提出候选解释，不是凭症状确定根因的判定器。Loss、attention map、分布统计或一次遮挡都不能单独证明原因；真机排查按[证据顺序](#real-world-diagnosis)推进，恢复能力按[固定分母评测](../system-design/evaluation.md#failure-recovery-evaluation)记录。

## 🔴 F1 · 虚假相关（Spurious Correlation）

### 症状
仿真/同分布完美，**换颜色/背景/位置就崩**

### 根因
模型找到了捷径——"任务 A 永远在桌子左边" → 学到的是**位置**不是**任务**

### 📎 典型实证
**[LIBERO-PRO (arXiv:2510.03827)](https://arxiv.org/abs/2510.03827)**：
- 标准设定：90%+
- 换物体/背景/位置的泛化设定：**0.0%**

### 🧠 检测建议
1. **遮蔽语言**：动作不变 → 忽略语言
2. **遮蔽部分视觉**：在匹配基线和足够重复下检查条件依赖；成功率不变不能单独证明未使用该模态，遮挡本身也可能改变输入分布
3. **换物体颜色**：崩溃 → 学了颜色特征

### 🧠 修复建议
- 采集时**刻意多样化**：初始条件、物体位置、背景纹理
- 引入 **RoboEngine 类背景替换**（📎 +210% vs 无增强）

---

## 🔴 F2 · 分布外偏移（OOD Shift）

### 症状
训练集 → 部署环境差一点点，**性能腰斩**

### 根因
数据覆盖不够——光照、相机位置、桌面纹理、物体尺寸

### 📎 间接实证
**[LIBERO-Plus](https://arxiv.org/abs/2510.13626)**：4 种扰动全部导致 95%→<30%

### 🧠 检测建议
主动构造边角案例（极端光照、罕见位置、陌生物体）测试

### 🧠 修复建议
- **Domain Randomization**（仿真侧）
- **多场景真实数据**（DROID 564 场景 是最佳实践）

---

## 🔴 F3 · 时序错位（Temporal Misalignment）

> 🧠 工程经验分类——但很少有论文专门量化对 VLA 性能的敏感度

### 症状
模型预测动作**总是慢半拍**，抓取时机差一帧

### 根因
图像时戳和动作时戳对齐差 **30-100ms**

### 典型诱因
- USB 相机软件时戳漂移（可达 50ms = 30Hz 视频 1.5 帧错位）
- ROS2 时间同步配置错误
- 硬件触发缺失

### 🧠 检测建议
画图对比连续帧的图像变化方向和 action 方向——应该**同步变化**

### 🧠 修复建议
- **硬件触发**（<0.1ms）
- **PTP (IEEE 1588)** 或 **ROS2 /clock** 同步（5-10ms）
- 采集后用**光学事件**（闪光灯）标定时延

---

## 🔴 F4 · 坐标系/动作漂移（Frame Drift）

> 🧠 工程经验——常见痛点

### 症状
**同一个模型，上周跑得好，这周不行**

### 根因
- 相机位置变了没重新手眼标定
- 机器人零位漂移
- 新批次采集员坐标系定义不同（比如 EE 原点放在末端 vs 工具中心）

### 🧠 检测建议
对比新旧数据的 EE 轨迹统计分布；均值／方差差异是漂移线索，也可能来自任务或采样变化，需结合标定、来源和回放核查。

### 🧠 修复建议
- 每次重装相机**必须**重手眼标定
- 元数据里记录变换矩阵（`T_base_to_camera` / `T_base_to_world`）
- 按批次分 chunk 训练，避免多批次混训

---

## 🔴 F5 · 语言-动作解耦（Language-Action Decoupling）

### 症状
**换任务描述，模型行为不变**

### 根因
语言标注是模板化的（`pick up the {obj}`）→ 视觉已经有足够信息识别任务 → 语言成摆设

### 📎 论文证据
- **[LIBERO-PRO](https://arxiv.org/abs/2510.03827)**：做了语言消融
- **[LIBERO-Para (arXiv:2603.28301)](https://arxiv.org/abs/2603.28301)**：
  - vision-only: **44.6%**
  - language-conditioned: **47.8%**
- **边界**：这两个分数本身不能证明完全忽略语言；需核对原评测设定、样本不确定性及有语言歧义任务的对照。

### 检测方法（黄金标准）
**语言消融** —— mask 语言看成功率是否下降

### 🧠 修复建议
1. 用 **LLM 重写**同一任务的多种表述：
   - "pick up the red block"
   - "grab the crimson cube"
   - "move the scarlet piece"
2. 让视觉**不能单独识别任务**——同一场景布置多个物体，必须靠语言消歧
3. 引入需要**世界知识**的指令（"pour a small amount"——"small" 不是视觉可见的）

---

## 🔴 F6 · 动作分布偏斜（Action Distribution Bias）

> 🧠 作者归纳 · 间接证据：RoboMIND 2.0 的 5K 失败案例设计动机

### 症状
模型在常见动作上表现好，**罕见动作（回退、重试、微调）完全不会**

### 根因
只收集"完美 demo" → 模型没见过"失败后怎么恢复"

### 典型现象
抓取失败后模型**卡住不动**（不会重试）

### 🧠 检测建议
部署时**人为制造偏离态**（挪一下物体）→ 看模型能否自动纠正

### 🧠 修复建议
1. **保留失败 + 恢复轨迹**（📎 RoboMIND 2.0 的 5K 失败案例专门应对此问题）
2. **DAgger 类数据增强**：部署时收集"模型跑歪 + 人工救场"的混合数据
3. **动作扰动**：训练时随机扰动专家动作然后学"纠正回来"

## 🎯 诊断决策树（真机不 work 时的第一步）

```text
固定一份失败片段 + checkpoint / 数据 / 配置版本
    ↓
实际训练 / 部署输入能否按声明的时间、坐标、动作语义回放？
    ├─ 不能 / 证据不全 → 先修记录、转换或接口，保留原始片段
    └─ 能 → 分开看“策略下发目标”和“实测运动”
              ├─ 目标平稳、实测跟不上 → 查控制接口、跟踪和硬件条件
              ├─ 目标本身跳变 / 已过时 → 查观测帧龄、推理、队列和chunk交接
              └─ 时序与跟踪在约定范围内
                    ├─ 换位置 / 视野 / 背景 / 指令才失败 → 测覆盖与条件依赖
                    └─ 抓空 / 滑落后仍走原流程 → 单独测失败检测与恢复
    ↓
一次只改变一个解释变量，保存支持和反对该解释的结果
```

箭头决定**下一项查什么**，不宣称已定位根因。动作表示、归一化、相机映射、控制器和数据覆盖可能共同失效；先定位不等于忽略其他层。

## 💡 真机排查流程：从可复盘记录到同条件对照

> **工程建议，不是已执行的机器人测试。** 不重复F1-F6的背景解释；这里规定检查顺序、最小交付证据和可以作出的结论。

### Step 1：冻结失败与输入契约

保留一次失败前后的连续记录、任务判据、checkpoint hash、代码／数据revision、标定、normalization统计量、动作表示、相机名称与顺序。数采字段直接复用[批次验收记录](../deployment/robot_data_collection_acceptance.md#collection-acceptance-record)。

从**实际loader和部署预处理之后**回放同一片段；区分“文件里有此模态”和“模型实际收到此模态”。先查command／measured state、joint／EE、绝对／增量和参考时刻，再讨论数据量或换模型。缺日志只记待验，不能反推模型没有能力。

### Step 2：把策略输出、排队与执行分开量

用同一时钟或有明确映射的时基关联：观测采集、输入就绪、推理开始／结束、动作块入队、命令下发和实测状态；同时保存chunk ID、动作步索引、取消／丢弃原因。时间映射不可靠时，先修测量，不能据拼接曲线定因。

| 观察到什么 | 下一项测什么 | 本步不能直接断言什么 |
|---|---|---|
| 目标平稳，实际关节／末端抖动或滞后 | 在既有安全范围内检查同目标回放的跟踪误差、控制模式与接口单位 | 不能直接归因于模型或未经验证就改PID／控制模式 |
| 目标在块边界跳变 | 将块内与块间分开；记录帧龄、实际执行horizon、推理及网络时延分布 | 不能只靠加平滑认定根因解决 |
| RTC更顺，却更易抓空 | 固定权重、布局、控制频率和试验预算，对齐sync／async无RTC／async有RTC的可比条件 | 不同条件的样片不能证明RTC提高成功率 |
| 全局相机能看到目标，腕相机看不到时失败 | 先核输入映射，再在预先定义的视野组合中比较 | 不证明模型只看腕相机，attention map也不能单独证明 |
| loss低但闭环失败 | 核loss定义、归一化、split和每任务结果；检查执行链路与覆盖 | 不直接等同过拟合；也不能凭低loss验收 |

网络、推理和控制频率分开报告；不要只报平均GPU推理时间。平滑度、完成时间、成功数／总数和人工介入分别记录，不能用其中一项替代其他项。

### Step 3：在可复盘基线上做单变量对照

先确认问题可重现，再一次只改变一个因素，例如图片传输方式、chunk参数、某路观测或一个布局条件；固定其余设置并重复试验，记录分子／分母及失败阶段。同步／异步模式难以完全对齐的差异要写明。滤波位置、截止参数、引入的延迟和跟踪误差也须记录，不把视觉上更顺等同修复。

遮挡、换指令或改state可用于检验候选解释，但它们也会改变输入分布；需有未干预基线，不能从单次无变化推出某模态没有作用。Loss异常同样可能涉及统计量、优化、加载或划分问题，不能只凭曲线认定标注错误。

### Step 4：把失败恢复与修改后的回归分开验收

抓空、滑落、左右臂误选后继续原动作，均先保存失败时刻、阶段和后续行为，再按[失败恢复评测](../system-design/evaluation.md#failure-recovery-evaluation)检验检测、重试与最终完成。不要以未训练的新恢复示教宣称问题已解决。

修补后复跑原失败条件及原来能成功的留出条件；对照预算、版本和成功判据一致。结案记录采用：`现象 → 候选解释 → 本次唯一改动 → 支持／反对证据 → 剩余解释 → 回归结果`。证据不足时写“现象缓解／原因未定”，不写“根因已修好”。
